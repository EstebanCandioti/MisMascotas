CAPÍTULO 01

El mapa completo

Primero separá las responsabilidades.

Un webhook es una petición HTTP que Mercado Pago inicia para avisar que cambió algo. MisMascotas verifica quién la envió, guarda el aviso y responde. Más tarde, otra ejecución del backend consulta a MP y decide qué efecto corresponde.

1 · RecibirFirma + JSON + IDsController y receptor
→
2 · PersistirBandeja PostgreSQLCommit antes del 200
→
3 · ConsultarEstado actual en MPProcesador periódico
→
4 · AplicarPago + cobertura + eventosTransacción de negocio
→
5 · RegistrarResultado y auditoríaEscrituras posteriores

Todo esto corre en una instancia del backend. No hay RabbitMQ, Kafka ni un servicio externo de colas: la bandeja es una tabla de PostgreSQL y el trabajador es un método Java que Spring invoca periódicamente. Supabase aloja PostgreSQL en desarrollo; Docker permite probar con otra base aislada.

Tres hechos diferentes
  • 200 OK: el receptor aceptó el aviso; para un tópico admitido, la fila quedó confirmada o ya existía.
  • payment.status = approved: MP informa que ese pago fue aprobado. Falta verificar su relación, importe, moneda y condiciones.
  • COMPLETADA: terminó el trabajo local de esa notificación. También puede ser una cuota rechazada definitivamente o una pausa, sin otorgar Premium.

El front inicia la suscripción a través de una ruta autenticada y abre initPoint. El webhook recibe novedades de MP. Ninguna notificación recibida equivale por sí sola a una orden de dar Premium.

Cómo leer esta guía

Los capítulos 2–7 explican los datos, Spring y la recepción. Los capítulos 8–14 recorren el procesamiento, las transacciones y la cobertura. Después vienen el simulador, el diagnóstico y el código completo. Los fragmentos numerados son del repositorio; las tablas, diagramas y simulaciones son explicaciones didácticas.

Los seis identificadores

Todos son IDs; identifican cosas diferentes.

NombreQuién lo generaQué representa / dónde se usa

preapproval.idMPLa suscripción remota o mandato de cobro recurrente. Se guarda en suscripcion.id_suscripcion_mercadopago.
external_referenceLo propone MisMascotasEn este proyecto es el UUID local enviado a MP al crear el preapproval. Permite corroborar la asociación; no sustituye los demás controles.

Ejemplo inventado para estudiar:
suscripción local:        7cfb… (UUID)
preapproval remoto:      pre-A

factura/cuota:           8001
pago:                    9001

data.id cambia de significado según type: con subscription_preapproval identifica el preapproval; con subscription_authorized_payment identifica la cuota. Usarlo siempre como ID de pago consultaría el recurso equivocado.

Dos formas distintas de repetición

  • Mismo aviso reenviado: el mismo ID de notificación no crea otra fila.
  • Otro aviso del mismo recurso: se guarda otra fila y se vuelve a consultar el recurso actual. Esto permite observar que una cuota antes rechazada luego fue pagada.

Además, dos notificaciones distintas del mismo pago no pueden acreditar dos meses: las restricciones de unicidad de pago y la lógica transaccional protegen el efecto económico.

Qué es el proxy y por qué hay dos servicios

Cuando otro bean invoca el servicio transaccional, normalmente pasa por un objeto intermediario de Spring. Ese intermediario abre la transacción, llama al método real y confirma antes de entregar el resultado. Una llamada de un método a otro de la misma instancia no pasa por ese intermediario en el modo habitual de proxies.

Procesador → proxy de SuscripcionCicloService
                 └─ consultas HTTP, NOT_SUPPORTED
                 └─ proxy de SuscripcionCicloTransaccionalService
                        ├─ abre transacción
                        ├─ registrar(...)
                        └─ commit / rollback → recién devuelve al llamador

Esta separación permite consultar MP sin retener un bloqueo del usuario durante la espera de red. También permite capturar una excepción de integridad después de que el proxy haya revertido la escritura.

CAPÍTULO 04

La petición HTTP, de punta a punta

El receptor hace poco trabajo y lo confirma antes de responder.

POST /webhooks/mercado-pago?data.id=8001
Content-Type: application/json
x-request-id: identificador-del-envio
x-signature: ts=...,v1=...

{"id":"aviso-01","type":"subscription_authorized_payment","data":{"id":"8001"}}

Este ejemplo muestra la estructura; no contiene una firma válida lista para enviar. El controller recibe el cuerpo como String. El servicio verifica la firma y recién después usa JsonMapper.readTree para construir el árbol JSON.

  1. Secreto ausente: 503.
  2. HMAC inválido: 401, aunque el JSON también sea inválido.
  3. JSON válido: debe ser objeto, con type textual no vacío.
  4. Tópico ajeno al alcance: acepta y descarta el aviso firmado, sin persistirlo.
  5. Tópico admitido: valida ID de notificación e ID de recurso; admite texto no vacío o entero. El data.id del cuerpo debe coincidir exactamente con el de la URL.
  6. INSERT en transacción corta. Al retornar execute, el commit ya terminó.
  7. El controller responde con el código HTTP y cuerpo vacío.
HTTPQué significa aquí¿Se intentó guardar?
200Aviso admitido confirmado, duplicado o tópico ajeno descartado.Sí para tópico admitido; no para ajeno.
401Firma ausente o inválida.No.
400JSON/tipo/IDs inválidos para el contrato aplicable.No.
503Secreto ausente o fallo al abrir, escribir o confirmar la transacción.Puede haber fallado antes, durante o al confirmar.

El receptor no espera el resultado del cobro. Si el guardado o su commit falla, no devuelve un éxito de recepción. Si la base confirmó pero se perdió la respuesta HTTP, un reenvío encuentra la misma clave primaria. Ese caso exige deduplicación aun con un backend perfectamente sano.

La tabla muestra los resultados controlados de este receptor. Una excepción inesperada que no capture ese código puede recorrer el manejo general de errores del backend; no hay que interpretar esos cuatro códigos como garantía de que cualquier defecto imaginable queda clasificado.

El action y la fecha del aviso no ordenan directamente la transición de negocio: el procesador consulta el recurso actual. Es una elección que reduce la dependencia del orden de entrega.

CAPÍTULO 05

Firma, JWT y credenciales de MP

Tres secretos con tres propósitos.

MecanismoQuién lo presentaQué permite
JWT de MisMascotasFront / Postman del usuarioAutenticar al usuario en rutas como iniciar, continuar o reemplazar.
Secreto HMAC del webhookLo comparten la configuración de MP y el backendVerificar la firma del aviso entrante. No es el access token de la API.
Access Token de MPEl backend al llamar a la API de MPConsultar o gestionar recursos del vendedor. Viaja en el header de las peticiones salientes.

Spring Security y JwtFilter dejan pasar únicamente el POST exacto del webhook sin JWT. La autenticación de esa ruta la hace la firma. Esto permite que MP avise sin iniciar sesión como un usuario de MisMascotas. CORS restringe ciertos accesos desde navegadores; no verifica a MP y no sustituye HMAC.

Cómo se calcula HMAC en este código

texto canónico = "id:" + dataId + ";request-id:" + requestId + ";ts:" + timestamp + ";"
firma calculada = HMAC-SHA256(secreto, UTF-8(texto canónico))
firma recibida  = bytes de los 64 caracteres hexadecimales de v1
comparación    = MessageDigest.isEqual(calculada, recibida)

HMAC prueba que quien construyó la firma conoce el secreto para esos valores. No cifra el aviso. Esta firma tampoco es un hash de todo el JSON: se verifican los campos del texto canónico y después la coherencia del recurso del cuerpo. El cobro se acredita con consultas autenticadas a MP.

El parser rechaza campos de firma ausentes, duplicados, desconocidos o mal formados; ts debe contener dígitos y v1 debe tener 64 dígitos hexadecimales. MessageDigest.isEqual se usa para comparar los bytes de la firma.

Lo que el validador actual no agrega

No aplica una tolerancia de antigüedad a ts, y conserva literalmente el ID, el request ID y el timestamp, sin normalizarlos. La clave primaria deduplica el ID de aviso, pero no equivale a una política completa de protección contra replay. Son límites del alcance actual, no nuevas funcionalidades implementadas por esta guía.

Contrato externo: Webhooks de suscripciones de MP. Los detalles estrictos anteriores describen MercadoPagoFirmaWebhook, no una garantía sobre todos los formatos que MP pudiera emitir.

CAPÍTULO 06

Qué hay dentro de una transacción

Una frontera de confirmación en PostgreSQL.

Una transacción agrupa operaciones SQL: si confirma, se conservan juntas; si se revierte, se deshacen sus escrituras. La controla el gestor de transacciones de Spring sobre la conexión a la base. No es una copia del objeto Java ni una función que sólo guarda el before y el after.

En la confirmación de un cobro, la transacción contiene la lectura bloqueante del usuario, la relectura de la suscripción, controles de duplicados, la inserción del pago, la cobertura, la bandera Premium y los eventos pendientes de auditoría. La serialización de snapshots se ejecuta durante esa operación, y las filas resultantes participan en el mismo commit.

OperaciónQué haceQué no implica
saveEntrega cambios a JPA; SQL puede diferirse hasta flush.No garantiza commit.
saveAndFlushFuerza sincronizar SQL con la base dentro de la transacción; puede descubrir restricciones inválidas.Todavía puede revertirse.
CommitConfirma la transacción en PostgreSQL.No confirma otra transacción ni un pago remoto.
RollbackRevierte las escrituras de esa transacción.No devuelve dinero ni deshace una llamada HTTP a MP.

Propagación: qué hacer si ya existe una transacción

PropagaciónSi hay una transacciónSi no hayUso actual
REQUIREDParticipa en la existente.Abre una.Escrituras de ciclo y vencimiento; también el template del resultado de bandeja.
REQUIRES_NEWSuspende la anterior y abre otra independiente.Abre una.Recepción con template; procesar log de auditoría.
MANDATORYParticipa.Falla.Encolar evento de auditoría: prohíbe guardarlo fuera del cambio auditado.
NOT_SUPPORTEDSuspende la existente mientras corre el método.Ejecuta sin transacción.Orquestación de consultas de SuscripcionCicloService.

REQUIRES_NEW no significa “después del commit”. Si se lo llama en medio de una operación, puede confirmar mientras la transacción exterior todavía está abierta y más tarde falla. En la recepción no hay una transacción de negocio exterior que deba acompañar al aviso; en auditoría, el procesador toma eventos que ya fueron confirmados por la operación original.

En esta ruta, una excepción de ejecución o de acceso a datos que sale del método transaccional provoca rollback. Capturarla dentro del método y devolver un éxito podría cambiar ese resultado; por eso importa dónde se captura. Las reglas de Spring también permiten configurar otras políticas de rollback; no hay que inferirlas sólo por el nombre de una excepción.

Los commits del recorrido

La recuperación conecta transacciones independientes.

A · Recepción

INSERT en bandeja.

Commit A → HTTP 200
Sin transacción de escritura

GET factura, pago y preapproval según el caso.

Validación remota
B · Negocio

Pago + suscripción + usuario + eventos de auditoría.

Commit B
C · Resultado

Estado, motivo, próxima fecha y observación de las filas capturadas.

Commit C
D · Auditoría posterior

Log y marca de evento procesado, por evento.

Commit D

Estas letras son nombres didácticos. No hay un coordinador de transacciones distribuido. Las consultas HTTP suceden antes de B; el guardado de C sucede después de evaluar el recurso y, si correspondía, después de B.

Se corta aquíLo duraderoCómo continúa
Antes de ANo hay aviso nuevo.MP debe volver a entregar; si el receptor falla devuelve 503.
Después de A, antes de BAviso pendiente.El scheduler lo encuentra al volver a arrancar.
Durante BAviso previo; ningún cambio parcial de B.Si falla la escritura, rollback y clasificación/reintento o revisión según el error.
Después de B, antes de CPago, cobertura y eventos ya guardados; bandeja aún pendiente.El próximo procesamiento detecta YA_CONFIRMADA; no vuelve a sumar cobertura.
Durante CResultado anterior de las filas del grupo.Se revierte C. Si seguían disponibles, pueden entrar en la siguiente tanda.
Durante DNegocio confirmado; evento pendiente.Rollback del log y su marca. La cola de auditoría vuelve a intentarlo.

Es válido ver Premium activo mientras la notificación todavía está pendiente si falló C. También puede verse Premium activo antes de que aparezca el log final. Esas ventanas existen por diseño; las restricciones, los eventos persistentes y las operaciones idempotentes permiten cerrarlas.

CAPÍTULO 08

La bandeja: una cola en una tabla

Qué guarda, qué conserva y cómo agrupa.

NotificacionMercadoPagoRepository usa JdbcTemplate con SQL explícito. Los valores se pasan como parámetros; no se concatenan datos del aviso al SQL. Para la recepción, la base resuelve en una sola operación si inserta o si la clave ya existe.

Hacer primero “SELECT para saber si existe” y después INSERT dejaría una carrera entre ambos. ON CONFLICT ... DO NOTHING, junto con la PK, resuelve la disputa en PostgreSQL. El reenvío no sobrescribe el tópico ni el recurso originales.

CamposSentido
id_notificacion, topico, id_recursoIdentidad del aviso y del recurso a consultar.
recibida_en, procesada_enRecepción y finalización exitosa del trabajo local. En REVISION, procesada_en queda nulo.
estado_procesamiento, ultimo_motivoPENDIENTE / COMPLETADA / REVISION y el diagnóstico concreto.
proximo_procesamiento_enDesde cuándo es elegible. Nulo en finalizados o revisión.
intentos_temporales, primer_fallo_temporal_enEpisodio activo de fallos técnicos.
intentos_pendientes, primera_comprobacion_pendiente_enConsultas locales con cobro inconcluso y comienzo del horizonte local.
estado_factura_mp, estado_pago_mp, detalle_pago_mp, id_pago_mpÚltima observación remota que pudo guardarse.
intento_mp, fecha_debito_mp, proximo_reintento_mpDatos informados por MP para diagnóstico. No ordenan al backend cobrar.

Cómo evita consultas repetidas en una tanda

  1. Busca hasta 20 filas PENDIENTE cuya próxima fecha ya llegó, ordenadas por próxima fecha, recepción e ID.
  2. Un conjunto de Java recuerda la pareja (topico, id_recurso) ya vista en esa tanda.
  3. Para cada pareja, captura todos sus IDs pendientes antes de llamar a MP, incluso otros con fecha futura.
  4. Evalúa el recurso una sola vez y guarda el mismo resultado para ese conjunto capturado.
  5. Un aviso que llega durante la consulta no estaba capturado: se deja para otra evaluación.

Así, una nueva notificación rompe la espera diaria de una cuota: su fecha inicial está disponible ahora. Una fila histórica en REVISION no se reabre ni se sobrescribe; otro ID nuevo puede resolver el recurso.

Los antecedentes se reúnen por tópico y recurso: el primer pendiente y su contador se conservan incluso entre notificaciones históricas; el episodio técnico se reconstruye con filas aún pendientes. Recibir otro aviso o reiniciar el backend no reinicia por sí solo el plazo de diez días.

Límite del lote

20 limita las filas candidatas iniciales, no necesariamente los recursos ni el total de filas actualizadas. Agrupar un recurso puede incorporar más de 20 filas pendientes. La bandeja conserva la observación más reciente, no el JSON completo ni un historial de cada consulta.

Semántica SQL: INSERT / ON CONFLICT en PostgreSQL.

CAPÍTULO 09

Quién procesa y cuándo

Un método secuencial del mismo backend.

fixedDelay espera 30 segundos después de terminar la invocación anterior. Si una tanda tarda 12 segundos, la siguiente comienza aproximadamente 42 segundos después del inicio anterior. No se crea un temporizador por factura: la fecha está guardada en PostgreSQL y la tanda busca las que ya están disponibles.

La primera tanda también espera 30 segundos por defecto. Cada recurso se atiende uno por uno; luego se ejecuta el barrido de vencimientos. synchronized impide que dos llamadas se solapen en esa instancia de ese objeto. No coordina dos JVM ni reemplaza un lock distribuido.

No hay una reserva UUID de cinco minutos ni FOR UPDATE SKIP LOCKED en esta bandeja de MP. Sí existe este último mecanismo en el procesador separado de auditoría. Conviene no confundirlos al leer el repositorio.

PropiedadValor por defectoEfecto
mercadopago.notificaciones.scheduler-habilitadotrueHabilita el bean; apagarlo detiene también su barrido de vencimientos.
mercadopago.notificaciones.intervalo-ms30000Espera entre tandas terminadas.
mercadopago.notificaciones.demora-inicial-ms30000Espera inicial.
mercadopago.notificaciones.tamano-lote20Límite inicial de candidatas y de usuarios a evaluar por vencimiento.

Una fecha programada significa “no consultar antes de”, no una hora exacta garantizada. Influyen la carga, la duración de HTTP, el arranque y la disponibilidad de la base. Si cae el proceso, no se pierde un timer en memoria: la fecha pendiente permanece en la tabla.

CAPÍTULO 10

Cómo se acredita un cobro

Estado aprobado más identidad y condiciones verificadas.

LlamadaQué aporta al proyectoControl
GET /authorized_payments/{id}Cuota: ID, estado, preapproval_id, external_reference, payment.id, importe, moneda y metadatos de intento.Debe coincidir con el recurso esperado y la suscripción local.
GET /v1/payments/{id}Pago individual: ID, estado, detalle, importe, moneda, date_approved.Debe ser el pago asociado; se comprueba su resultado real.
GET /preapproval/{id}Mandato: identidad, referencia, estado, recurrencia, importe, moneda, next_payment_date y last_modified cuando vienen.Debe corresponder al plan del backend y a la suscripción local.

La consulta del pago se hace si la cuota tiene payment.id. La consulta adicional del preapproval para acreditar sucede cuando la cuota está processed y el pago approved. Un evento de cambio de suscripción consulta directamente el preapproval.

La cadena de confianza

  1. El aviso firmado proporciona un recurso a consultar.
  2. La cuota obtenida debe tener ese mismo ID, un preapproval conocido y la referencia UUID local.
  3. El detalle del pago debe tener el ID indicado por la cuota y un estado coherente.
  4. Para acreditar: cuota processed + pago approved; importe y moneda de cuota y pago iguales al catálogo; fecha de aprobación presente.
  5. El preapproval debe coincidir en ID, referencia, importe, moneda, frecuencia y unidad. Para un cobro aprobado se admiten authorized, paused o cancelación remota conocida.
  6. Dentro de la transacción se relee la situación local, con bloqueo: pudo haber cambiado mientras se esperaba a MP.

El importe se compara con BigDecimal.compareTo: 4000.0 y 4000.00 representan el mismo valor. El catálogo del backend decide el plan y su precio; el body del webhook y el navegador no los deciden.

El cliente concreto MercadoPagoClient implementa la interfaz MercadoPagoGateway. En producción usa HTTP; en muchas pruebas esa interfaz se reemplaza por una simulación. Ésa es la razón de separar la API de la lógica de negocio.

En este fragmento, restClient.get() prepara la petición, uri fija el recurso, header agrega el token del vendedor y retrieve().body(String.class) obtiene el cuerpo. El parser transforma JSON a datos del gateway y rechaza lo que no satisface el contrato. El try/catch lo convierte a MercadoPagoException; el procesador traduce esa excepción a un resultado de planificación.

HTTP exitoso tampoco alcanza

Un 200 de la API con identidad, JSON o fechas inconsistentes puede terminar en REVISION. Los JSON de MP tienen más campos que los records usados por este backend: el proyecto extrae un subconjunto. El visor de código incluye esos records.

CAPÍTULO 12

Los relojes y la política de reintentos

Consultar otra vez no equivale a volver a cobrar.

Hay dos motivos para volver a consultar: el recurso todavía no está resuelto o no pudimos consultarlo correctamente. PlanificadorNotificacionMercadoPago recibe el resultado, el reloj y los antecedentes; devuelve los campos a guardar. Es una función de cálculo: no hace HTTP ni SQL.

SituaciónDemora desde la evaluaciónHorizonte local
Recycling + rejected24 horas.10 días desde la primera observación local pendiente de ese recurso.
Waiting for gateway o scheduled sin pago5 minutos.El mismo horizonte de 10 días.
Timeout, conexión, 5xx o fallo inesperado transitorio1, 5, 15, 60 minutos; después 60 minutos.24 horas desde el comienzo del episodio técnico activo.
429Retry-After válido; si no, la secuencia técnica.Conserva los límites técnico y de negocio ya iniciados.

La próxima fecha se recorta al límite aplicable más cercano. Antes de declarar agotado un plazo se hace una última consulta: si ya hay una resolución válida se aplica. Si sigue pendiente queda REVISION / PLAZO_COBRO_PENDIENTE_AGOTADO; si sigue fallando el episodio técnico, PLAZO_TEMPORAL_AGOTADO.

Ejemplo con ambos relojes

  1. Lunes 10:00: se observa recycling. Próxima consulta martes 10:00; horizonte local de negocio, jueves de la semana siguiente a las 10:00.
  2. Martes 10:00: MP devuelve 500. Empieza un episodio técnico y se consulta otra vez desde las 10:01.
  3. Martes 10:01: GET válido, sigue recycling. Se limpia el episodio técnico; el horizonte de negocio sigue contando desde el lunes.
  4. En cualquier momento, otro webhook con otro ID queda disponible y dispara una evaluación sin esperar la fecha diaria.

Retry-After admite segundos no negativos o fecha HTTP RFC 1123. Cero o fecha pasada dejan elegible para la próxima tanda; un valor mal formado usa el respaldo. Si alcanza o supera el plazo permitido, pasa a REVISION / RETRY_AFTER_FUERA_DE_PLAZO.

Dos ventanas distintas

Los diez días de MisMascotas empiezan cuando el backend observa el pendiente por primera vez. No se afirma que ése sea el inicio de la ventana real de MP. debit_date, retry_attempt y next_retry_date se conservan como observaciones; no se calculan fechas de cobro ni intentos bancarios a partir de ellos. La lógica no depende de que venga next_retry_date.

REVISION detiene la consulta automática de esas filas y deja su próxima fecha nula. No bloquea el webhook ni cancela el mandato: un aviso nuevo puede aportar una resolución. No existe un panel administrativo ni una automatización adicional para resolver esa revisión.

CAPÍTULO 13

El commit de pago y cobertura

Bloqueo, relectura e idempotencia.

Después de consultar MP, SuscripcionCicloTransaccionalService.registrar abre o participa en una transacción REQUIRED. Primero bloquea la fila del usuario y después relee su suscripción. Alta, reemplazo, cobro y vencimiento comparten ese orden.

Un bloqueo pesimista de escritura hace esperar a otro flujo que quiera tomar el mismo bloqueo de ese usuario hasta que termine la transacción. No bloquea toda la tabla ni el sitio; tampoco evita cualquier escritura de cualquier código que ignore el convenio. Aquí protege la decisión conjunta sobre suscripción y Premium. Las restricciones únicas de la base agregan una protección independiente.

  1. Verifica propietario, tipo de plan, IDs y estado local. Un intento marcado reemplazada no debe acreditarse como una nueva alta válida.
  2. Busca pagos por ID de transacción MP y por ID de factura MP.
  3. Si ya existe un pago coherente, devuelve YA_CONFIRMADA. Puede completar la factura que faltaba en un pago manual histórico; no vuelve a sumar meses ni a encolar auditoría.
  4. Si existe una asociación incompatible, devuelve revisión. La unicidad también frena carreras no previstas.
  5. Si es un pago nuevo, calcula cobertura, crea pago APROBADO, actualiza suscripción y bandera de usuario.
  6. Encola dos eventos: CREATE de pago y ACTIVATE de primera suscripción o UPDATE de renovación.
  7. Al salir por el proxy, confirma todo junto. Una falla que provoca rollback revierte también los eventos pendientes.

Por qué hay idempotencia en varias capas

CapaClave / controlEvita
RecepciónPK del ID de notificaciónDuplicar el mismo aviso.
NegocioIDs únicos de pago y factura + verificación de lo existenteAcreditar otra vez aunque cambie el ID del aviso.
Exclusión localLock de usuario y relecturaDecisiones simultáneas incompatibles sobre su cobertura.
AuditoríaUUID único de evento en el logDuplicar el log final del mismo evento.

La entrega de avisos puede repetirse; el objetivo es que el efecto persistido sea único. Decir “exactamente una entrega” describiría una garantía que esta arquitectura no tiene ni necesita.

Vigencia, cambios del mandato y vencimiento

Pagar, autorizar y cancelar tienen efectos distintos.

Ejemplo: si la cobertura vence el 16 de diciembre y el siguiente pago se aprueba el 15, la renovación se suma desde el 16. Si se aprueba el 18, se suma desde el 18. Enero 31 más un mes se ajusta al último día válido de febrero; no se suman 30 días fijos.

Eventos subscription_preapproval

Estado remoto verificadoResultado / efecto
pendingSUSCRIPCION_PENDIENTE. Se sincronizan metadatos; no se acredita.
authorizedSUSCRIPCION_AUTORIZADA o REACTIVADA. No concede tiempo nuevo sin pago.
pausedSUSCRIPCION_PAUSADA. Se guarda estado remoto; se conserva cobertura pagada.

estado_mercadopago es el estado observado del mandato. estado_id sigue siendo la relación al catálogo local: no se volvió a crear la columna legacy de estado textual. Pausa remota no agrega un nuevo estado local de catálogo.

Una respuesta con last_modified anterior al ya guardado no revierte ese estado. Si la fecha falta no hay comparación temporal posible. Los intentos reemplazados tienen protección adicional. Una suscripción cancelada puede reconocer un pago válido y conservar CANCELADA: acreditar cobertura no reactiva la autorización para próximos cobros.

El barrido de vencimientos

Después de la tanda se buscan hasta 20 usuarios con cobertura paga vencida. Por usuario, otra transacción bloquea su fila y relee todas sus suscripciones. Si alguna cobertura paga sigue vigente, conserva Premium. Las canceladas cuentan mientras tengan tiempo pagado.

Cuando corresponde, ACTIVA pasa a VENCIDA y se deshabilita Premium. CANCELADA conserva su estado. Se encolan eventos sólo por cambios reales. Una cuenta Premium manual sin suscripciones pagas no se deshabilita por ese barrido.

Dos límites concretos

Una suscripción con pago aprobado pero sin vencimiento causa rollback y log del fallo de esa evaluación; no crea automáticamente una fila REVISION en la bandeja. Tampoco existe una excepción para otorgar un mes desde la confirmación local tardía: si se descubre un pago muy antiguo, se guarda su fecha real y se calcula desde las fechas acordadas; la bandera depende de que la cobertura resultante siga vigente.

CAPÍTULO 15

La auditoría: otra cola y otro commit

El sistema actual usa eventos persistidos para estos flujos.

El flujo de cobro no se limita a un listener en memoria AFTER_COMMIT. Guarda un evento pendiente de auditoría dentro de la misma transacción del pago. Después, un procesador separado lo convierte en un log final. Este patrón se conoce como outbox transaccional.

Transacción BCambia el negocio y guarda el evento.MANDATORY al encolar
→
Evento confirmadoSnapshot before/after persistido.Puede esperar un reinicio
→
Transacción DEscribe log + marca el evento.REQUIRES_NEW por evento

MANDATORY obliga a que el llamador ya tenga transacción. El método recibe actor, entidad, acción, ID y snapshots explícitos. Los serializa a JSON y guarda la fila pendiente. En los cambios automáticos el actor es nulo y el snapshot tiene un origen como WEBHOOK_MERCADO_PAGO o VENCIMIENTO_PROGRAMADO: no se atribuyen falsamente al usuario dueño.

Qué hace el procesador de auditoría

  1. Su tarea periódica espera 5 segundos por defecto y busca hasta 100 eventos.
  2. Por evento abre REQUIRES_NEW y toma la fila pendiente con FOR UPDATE SKIP LOCKED.
  3. Si no existe log para ese UUID, lo crea. Su fecha refleja la fecha del evento, no la hora tardía del trabajador.
  4. Marca el evento procesado y confirma log + marca juntos.
  5. Si falla, se revierten ambos. Otra transacción intenta registrar el fallo; conserva el pendiente para una ejecución posterior.

Desde el tercer fallo se reporta como persistente en logs. El procesador actual de auditoría no usa la secuencia de 1/5/15/60 minutos de MP: vuelve a intentar mediante su propia tarea periódica, sin un máximo de intentos ni un backoff equivalente implementado.

EnfoqueQué ocurre si cae el proceso después del commit del negocioSituación en MisMascotas
Listener sólo en memoria AFTER_COMMITDepende de que llegue a ejecutar el listener; por sí solo no deja un pendiente duradero.No es el mecanismo usado por este flujo.
Evento pendiente en la misma transacciónEl evento ya está en la base y puede retomarse.Cobros, ciclo, vencimiento y edición de mascota migrada.
Log REQUIRES_NEW antes del commit exteriorPuede quedar un log aunque el negocio se revierta después.El aspecto histórico sigue existiendo para otros flujos; no debe confundirse con este contrato.

Por eso una falla del log final no deshace un pago ya confirmado. En cambio, una falla al encolar el evento dentro de B sí revierte el cambio de negocio. La diferencia es en qué transacción ocurrió.

Un HTTP 503 del receptor y un HTTP 503 de la API de MP son cosas diferentes: el primero responde a MP que no confirmó la recepción; el segundo ocurre en una consulta posterior y puede programar un reintento local.

Si PostgreSQL no permite guardar un nuevo resultado, tampoco se puede garantizar que quede persistido el backoff. La fila conserva lo anterior y puede reaparecer en la siguiente tanda. No hay una base alternativa donde guardar el fallo.

La clasificación es conservadora pero no infalible: una excepción inesperada se reintenta temporalmente hasta su límite aunque su causa real pudiera ser un defecto permanente. El motivo y la clase de excepción ayudan a investigarlo; no reemplazan el diagnóstico.

CAPÍTULO 19

Cómo investigar un caso sin adivinar

Seguí la cadena de IDs y la frontera que falló.

  1. Recepción: ¿hubo 200/401/400/503? Un body vacío en 200 es normal. Verificá URL, headers y tópico.
  2. Bandeja: buscá el ID de aviso. Si el tópico era ajeno, su descarte firmado puede ser correcto.
  3. Planificación: mirá estado, motivo, próxima fecha y antecedentes. PENDIENTE con próxima fecha futura puede ser funcionamiento esperado.
  4. Recurso: cuota o preapproval según tópico; nunca intercambies sus IDs con payment.id.
  5. Negocio: ¿existe un pago por ese ID MP o factura? ¿Qué vencimiento quedó guardado? ¿La bandera del usuario coincide con su cobertura?
  6. Auditoría: distinguí evento pendiente de log final. Un log que todavía no aparece no prueba que el pago haya fallado.
  7. Procesos: si todo está vencido para procesar pero no cambia, revisá scheduler habilitado, arranque, migración y logs de la tanda.

Dos recorridos que conviene distinguir al programar

El scheduler llama a evaluar(notificacion) y guarda planificación + observación en su template. El método histórico procesar(id) puede marcar una completada mediante otro servicio, pero no persiste toda esa política de pendientes. No es equivalente reemplazar uno por el otro.

La confirmación manual del primer cobro conserva su endpoint y su búsqueda de cuotas. El webhook del ciclo actual acredita la cuota concreta mediante SuscripcionCicloService; no necesita recorrer todas las cuotas para elegir el primer pago en cada renovación.

CAPÍTULO 22

Límites actuales que hay que conocer

Hechos observados; no cambios realizados.

  • Una instancia: el scheduler de MP no reclama trabajo con reservas distribuidas. Agregar instancias exigiría revisar esa coordinación; synchronized no se comparte entre procesos.
  • Latencia: la ejecución es secuencial. El cliente revisado no configura explícitamente sus propios timeouts de conexión/lectura; esta guía no inventa un plazo máximo para HTTP. Una consulta muy lenta demora los recursos siguientes y el barrido.
  • Revisión manual: REVISION no tiene un panel ni una resolución automática adicional. La evidencia está en filas y logs.
  • Observación parcial: la bandeja no es un historial completo de payloads ni de todos los intentos bancarios. Conserva los últimos metadatos guardados.
  • Firma: sin límite local de antigüedad y sin normalización del ID en el validador. Su alcance exacto se explicó en el capítulo 5.
  • Auditoría mixta: no todo el proyecto migró del aspecto histórico al contrato de eventos pendientes. Este flujo sí lo usa.
  • Devoluciones y contracargos: llevan a revisión; no hay cálculo automático de devolución de cobertura implementado para el MVP.
  • Estado remoto y tiempo: last_modified ausente impide aplicar el filtro de respuestas anteriores. No hay una transacción atómica que abarque MP y PostgreSQL.
  • Confirmación muy tardía: no se regala una vigencia distinta de la calculada desde aprobación/vencimiento. No se añadió una regla nueva por antigüedad en esta guía.

La documentación explica el estado del código. Para cambiar cualquiera de estos límites hace falta una decisión de alcance y una tarea concreta; generar esta guía no modifica el backend, su seguridad, las credenciales ni los datos.

CAPÍTULO 23

Comprobá que entendiste la arquitectura

Preguntas pequeñas con consecuencias importantes.

¿Puede haber 200 del webhook sin Premium activo?

Sí. 200 confirma recepción; el cobro puede seguir pendiente, estar rechazado, pertenecer a una pausa o requerir revisión.

¿Puede estar Premium activo y la bandeja pendiente?

Sí. B pudo confirmar el pago y C fallar al guardar el resultado. El reintento reconoce YA_CONFIRMADA.

¿Un reintento local genera otro cobro bancario?

No. Estas reconsultas usan GET para observar. MP realiza sus propios reintentos de cobro.

¿Por qué no poner @Transactional a todo el scheduler?

Mantendría una transacción durante consultas de red y agruparía recursos independientes en una frontera demasiado grande. La implementación usa transacciones cortas para cambios concretos.

¿Por qué el lock del usuario si hay un solo procesador?

El usuario puede iniciar/reemplazar o confirmar manualmente por HTTP mientras el scheduler procesa. También vencimiento y renovación deciden sobre la misma bandera.

¿REQUIRES_NEW garantiza que el log ocurre después del negocio?

No. Sólo define independencia transaccional. Aquí el procesador de logs toma un evento que ya quedó confirmado junto al negocio; eso establece el orden.

¿Diez días implican pago rechazado?

No. Es el horizonte de observación local. Si la última consulta no resuelve, pasa a revisión; otro aviso puede volver a consultar.

¿Cancelar elimina inmediatamente el tiempo ya pagado?

No. Se guarda CANCELADA y se conserva cobertura hasta su vencimiento. Un pago válido pendiente puede reconocerse sin reactivar el mandato.

¿La página ejecutó los escenarios contra Supabase o MP?

No. Los controles interactivos son modelos didácticos offline. La evidencia de pruebas del backend está separada en el registro QA.
